⏺ Кратко: JWT — это формат токена, OAuth 2.0 — это протокол выдачи/обмена 
  токенов (которые часто и являются JWT). Так что выбор не «или-или», а «своя
  простая выдача JWT» vs «полноценный OAuth-флоу (обычно с теми же JWT внутри)».

  Свой JWT-сервис («обычный JWT»)

  - Реализация: POST /auth/register, POST /auth/login (логин+пароль →
  подписанный JWT), POST /auth/refresh, middleware Authorization: Bearer … в
  остальных сервисах.
  - Что делаешь сам: таблица users, хэширование (bcrypt/argon2), refresh-токены,
   ротация ключей.
  - Подпись: HS256 (общий секрет — дёшево, но секрет утекает в каждый сервис)
  или RS256/EdDSA (приватный ключ только у auth, остальные верифицируют
  публичным — правильнее для микросервисов).
  - Плюсы: 1 эндпоинт логина, легко тестировать, минимум зависимостей. Идеально
  для курсовой/учебного проекта, где фокус не на авторизации.
  - Минусы: ты сам отвечаешь за безопасность, нет «войти через Google», нет
  стандартизированных интеграций.

  OAuth 2.0 / OIDC

  - Два сценария: либо твой auth_service — сам OAuth-сервер (Authorization Code
  + PKCE, токен-эндпоинт, JWKS), либо ты делегируешь логин внешнему IdP (Google,
   Keycloak, Auth0) и просто валидируешь их токены.
  - Реализация заметно толще: redirect-флоу, state/PKCE, callback на фронте,
  refresh-токены в хранилище, JWKS-эндпоинт с ротацией ключей, scopes/audience.
  - Использование клиентом: сначала браузерный редирект на /authorize → callback
   с code → обмен code на токен → дальше уже Authorization: Bearer … как обычно.
   Для service-to-service — client_credentials grant.
  - Плюсы: стандарт, готовые библиотеки, легко прикрутить соц-логин, чёткое
  разделение «кто пользователь» (id_token) и «что разрешено» (access_token),
  готовые сервера типа Keycloak/Hydra если не хочешь писать своё.
  - Минусы: значительно больше движущихся частей, больше сценариев тестировать;
  для одного фронта и одного логина — оверкилл.

  Разница в коде сервисов-потребителей почти нулевая: в обоих случаях это одно
  middleware, которое читает Authorization: Bearer, парсит JWT, проверяет
  подпись (HS-секретом или по JWKS), достаёт sub/scopes. Различия — только в
  том, как ты этот токен раздаёшь.

  Рекомендация для этого проекта: свой JWT-сервис на RS256 с access+refresh. Это
   релевантно теме (анонимизация, аудит — то, ради чего проект) и не размывает
  фокус. OAuth/OIDC можно прикрутить позже как отдельную итерацию (или поднять
  Keycloak в docker-compose и переключиться, не трогая бизнес-сервисы —
  middleware-то одинаковое).
